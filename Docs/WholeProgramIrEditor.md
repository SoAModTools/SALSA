# Production editor cutover (WP6)

The executable opens `ProgramWindow`, backed by one `ProgramService` per workspace. Tabs contain script IDs, a paged outline model, and a stable selected subject. They do not contain an `SctEditSession`, mutable native document, full authoring history, or a script-wide instruction map.

For Dreamcast, use one disc per project. Editing both discs concurrently means opening two SALSA instances with separate disc extractions and workspaces; a combined multi-disc project is not supported. See [editing multiple discs](WorkspaceAndSources.md#editing-multiple-discs) for the workflow and current clipboard limits.

## Loading and persistence

Startup restores geometry and recent-item settings without opening a project. **File > Open Project** selects a saved authoring workspace directory; **Recent projects** and **Reopen saved project** open the recorded workspace immediately. Saved opening uses the existing exclusive-operation widget as a compact phase/progress/Cancel indicator, closes automatically after tab presentation, and expands only for diagnostics. It recovers pending workspace transactions, reads/decompresses `project.salsaproject`, restores the IR and lookup indexes, and restores saved tabs. It does not scan, hash, or decode extraction files. The extraction may be offline; stored source paths and fingerprints remain historical context until **Review source changes** or explicit resource inspection. Missing checkpoints and unsupported schemas fail visibly instead of starting a fresh import.

**File > Import Project** retains the full exclusive-operation workflow, including extraction/workspace configuration, progress, source decisions, and optional story analysis. Fresh import discovers and orders the SCT paths, then runs a continuously replenished worker pool. Each worker reads and hashes one file, retains its baseline, parses and normalizes that same immutable capture, and releases source bytes and SPICE graphs before taking another file. The complete dataset fingerprint is assigned to detached script baselines after the scan, before installation. Fresh native and supported v7 imports discover logical indexed messages and reduce recognized equivalent localization sequences before exposing the project. Saved projects restore their authored localization organization without rediscovery. Resident script tabs never parse their source again.

The existing exclusive-operation coordinator covers preparation, installation, catalog population, and sequential tab restoration. Progress reports actual phases and counts; unknown-duration phases remain indeterminate. Worker progress is buffered and delivered on the Qt thread at a throttled rate. Reassociation is a review inside that operation. Cancellation waits for a noninterruptible stage to return; filesystem commits finish safely. A failed or cancelled workspace preparation leaves the installed workspace unchanged. Cancellation during tab restoration keeps the new workspace and completed tabs and retains the unopened saved-tab records. Cancellation closes the operation after its worker and cleanup finish safely; it records an activity entry without presenting a cancellation acknowledgment page. Failures retain their diagnostic page.

Saving captures one checkpoint for binary/zstd-1 encoding and commits it through the workspace transaction service. Views, positions, language presentation, and saved tabs remain separate from execution content. Script IDs and selection IDs survive reopening. Save is project-wide because the journal and checkpoint belong to the workspace, rather than to individual document tabs.

Fresh native imports automatically commit their initial project after localization organization, before editor installation and the optional story-analysis choice. A failed initial save fails the import instead of presenting an unsaved project as complete. Legacy v7 imports already commit a project during conversion. Later edits, including optional story organization, use ordinary Save. Recent projects checks workspace manifests and checkpoint-file presence in the background, lists only saved checkpoints, and collapses duplicate path spellings. It does not decode projects or inspect source files to build the menu; unsupported checkpoints still report their diagnostic when opened.

After a fresh import, the same operation offers **Analyze story and cutscenes** or **Finish**. Finish opens instruction mode, including the semantic editor. Analysis covers the entire project, then offers the existing explicit module-organization choice within the operation. Select suggested sections and choose **Enable story authoring**, or Finish to leave organization unchanged. Cancelling optional analysis keeps the imported project open. Story tools can perform this analysis later. Reopening a saved workspace does not repeat this onboarding step.

Earlier development authoring containers are intentionally unsupported. Opening one reports its decoder diagnostic instead of replacing it with newly imported source content. Use a fresh workspace for a new native import. Supported Python SALSA v7 projects still use the trusted converter and review/commit workflow. Commit now creates the binary program directly through `LegacyProgramImport`, respecting reviewed metadata exclusions. The migration capsule remains in the workspace's import evidence. SALSA does not export v7 projects.

## Scoped editing and presentation

`outline` returns one page of direct children, with no instruction payload or descendant-body copy. The Qt tree requests at most 128 rows at a time. Its nodes occupy a flat slot vector; only requested containers and rows are represented. `read` can request an individual section, sequence, condition, action, or text. `descend=false` excludes nested instruction bodies, and `referencedText=false` excludes automatically following text references. Returned pool handles belong only to that immutable read result.

`locate` returns the ancestry of a stable subject for navigation and saved selection restoration. Script/section order, action ownership and nested construct ownership determine that path. It does not lower or analyze the script. Parameter changes refresh the affected label in place; sequence order changes invalidate only the fetched owning container. Script-layout receipts are distinct from edits inside a section. Aliases have a service-owned derived lookup that is invalidated by metadata changes, rather than a per-view copy of program identity.

The editor routes instruction and SCPT editing, prepared conditions, structured branch/loop insertion, moves/deletion, section edits, branch/case ordering, repeated parameter groups, explicit-flow promotion, text editing, aliases, variable meanings, entrypoint activation, and language membership through the production journal. Existing SCPT and formatted-message widgets are reused as detached typed-value editors. Their display bindings are translated by a captured authored-ID closure; they do not look up or mutate a native document. Generated instructions never become editable authoritative content.

Modules, entrypoints, language groups, item explanations, variable uses, and module effects are opened explicitly from Authoring tools. Opening a tab does not build story connectivity. Variable-use and generated-instruction lists use lazy models. Module story-effect inspection filters its default report to BitVar and ByteVar; the explicit variable query still permits all banks. Observations and user assertions remain distinct, and a variable write is not presented as proof of runtime reachability or a guaranteed final state.

Native publication and explicit generated-instruction inspection call the same revision-qualified materializer. Publication settings choose native byte order, text convention and wrapper independently of project compression. Replacing files in the source dataset requires the publication control to be selected. Missing MLD evidence does not gate publication. A stale or unsupported executable draft fails there with diagnostics.

Resolved jumps remain explicit, editable instructions in both outline modes. Their labels show the destination, such as `Jump → A18MAIN`; an interior destination also includes its stable action ID. A jump crossing a section boundary does not by itself receive a grouping warning. Unresolved targets and other grouping problems still report diagnostics. SALSA does not simplify away jumps to adjacent sections or replace them with subscript calls.

## Retirement and remaining presentation work

The old MainWindow, WorkspaceController/SctDocumentController, snapshot outline/parameter models, full-state authoring dialogs, and patch/rebase UI are excluded from the production Qt target. Historical sources remain available to their isolated regression targets and import-boundary helpers. There is no runtime switch back to the old authority, and no synchronization layer between it and the production service.

This cutover supplies a compact service-backed editor surface. It is not a claim that the earlier graph layouts, snippet/clipboard presentation, or every legacy convenience dialog has been redesigned and ported. Those old snapshot-dependent surfaces are not exposed by the new entry point. Imported folder/opcode-color presentation is retained in the checkpoint; its visual redesign remains separate. Optional MLD association inspection has a worker implementation, but its dialog currently has no caller in the production window. That implementation reads and qualifies only the selected asset, outside the SCT catalog fingerprint, and preserves authored targets. The earlier per-entry provider picker and tile-preview UI still require a scoped presentation port. G2 now exposes text creation through the dock and Edit menu; the variable-meaning dialog is still not wired to an action. These are incomplete UI capabilities, not restored features. The next workstream is [GUI/backend separation and capability restoration](WholeProgramIrProductionPlan.md#next-workstream--guibackend-separation-and-capability-restoration).

## Unified opening and source detection

Import Project keeps extraction-folder selection, workspace selection, source inspection, recovery decisions, editor presentation, and the optional story-analysis choice inside the full exclusive-operation widget. A new dataset receives an editable sibling-workspace suggestion. The native page can switch to the v7 importer; a successful v7 commit continues into workspace opening in the same operation. Saved projects use the separate immediate-opening path described above. File-browser dialogs only select paths.

Native source import asks SPICE to parse byte order and wrapper, then assess text using that same parse. Indexed dialogue supplies the dataset's main convention; footer evidence never votes on that decision. Ambiguous or text-light files inherit the dataset default before installation. Clear per-file recommendations and explicit main-convention overrides remain intact.

Dataset selection aggregates SPICE's viable indexed candidates per file, giving a unique candidate a full vote and splitting votes between discriminating ambiguous candidates. Unique recommendations and per-record support break ties; a remaining tie uses SPICE's stable descriptor order. SPICE does not rank tied candidates, so SALSA records this last choice as an import assumption rather than claiming certainty. Ambiguity alone no longer opens a required source-override review. If the main convention cannot decode an automatic-import record, a complete local SPICE interpretation is used when available; wholly undecodable content remains an incomplete draft with evidence.

Footer message and plain-string records are selected independently through SPICE's per-record interpretations. When complete alternatives tie, SALSA prefers Shift-JIS debug text (byte-7F, then 8140), with Windows-1252 as the other complete alternative. This accommodates mixed EU sources without classifying the dataset's platform/region or forcing its main encoding onto footer text. Tied choices are retained as assumptions with source-text identities. A main-convention override does not automatically override footer decoding. The lower-level explicit trusted-footer option remains available to callers that deliberately request it.

Imported text becomes ordinary editable Unicode/message content in the existing text editor. These defaults are not language restrictions or export targets. Source evidence stays on the imported baseline; changing a draft's text does not change its source bytes. Automatic import retains compact raw records only for undecided indexed text until the dataset default is resolved, then releases them. It does not reread or reparse entire SCTs for this resolution. Saved binary projects still bypass source detection on reopen.

Version-7 files retain decoded strings and normalized parameter data, not reliable original platform/region/text-encoding provenance. The existing trusted converter and metadata review remain in place. Its baseline-construction settings have defaults and optional conversion overrides, rather than mandatory platform/region questions. Raw legacy overrides may still need an explicit byte-order choice. A conversion profile is labelled as a conversion choice, not detected source identity.

Target availability, conditional platform blocks, and output-opcode suppression remain deferred. Export settings continue to be selected separately.

## G1 — Editor contracts and first component slice (implemented)

`SalsaCore/Editor/EditorBackend.h` is the Qt-free boundary for paged outline rows, revision-qualified inspection, parameter replacement and history. `ProgramBackend` implements it with the existing single `ProgramService`; it copies only selected display/parameter values and translates edits into existing journal commands. Shared authoring IDs now have a small independent header. No new ID allocator, storage format, native document authority or backend picker was introduced.

`ProgramWindow` is a small application shell. `ProgramWorkspaceController` composes its menus/docks and coordinates loading/persistence. `ScriptOutlineComponent`, `ProgramOutlineModel` and `InstructionInspector` depend on the editor boundary, with `EditorSessionPresenter` coordinating selection, revision-qualified worker delivery, local change notifications and Undo/Redo. These components do not include ProgramService, ReadScope or SctDocument snapshots. The inspector contributes its Edit parameter action; the presenter contributes history actions. Shell menus host those actions.

Select an instruction to see its parameters in the Instruction inspector dock. Select a parameter and choose Edit parameter, or double-click its row. G1 supports unsigned 32-bit decimal words and SCPT expression text, including addressed parameters within repeated groups. Other types remain visible with an explanation and use the existing selected-item editor. Apply creates one engine history operation; cancelling the parameter dialog leaves the committed value untouched. Undo/Redo refresh the same selection and affected outline rows without a whole-tree reset for scalar edits.

Inspection is asynchronous. Selection/revision/session changes invalidate late deliveries; replacing selection requests stop on its previous read. Operation work is still under the exclusive-operation coordinator, including cancellation and diagnostics. Hidden tabs do not take over inspection when their model changes. Existing tool drafts are loaded only on invocation, avoiding a duplicate IR read on ordinary selection.

This closes G1's narrow vertical slice, not the full inspector or semantic editor restoration. The current advanced tool implementations remain temporarily in the workspace coordinator and still use ProgramService/ProgramValueDialog; they must migrate into their feature components in G2-G6. Moving those methods out of the window is not counted as restoring or decoupling their capabilities. The following G2 checkpoint supersedes those remaining everyday-editing gaps.

## G2 — Everyday script editing components (implemented)

Each script tab has Instructions and Semantic modes. Both address the same persistent IR actions, arms, conditions and body sequences through stable IDs. Native import uses SPICE analysis to create supported conditional, While and Switch constructs directly. There is no separate display-only group or promotion step required to edit an imported group. Empty bodies retain their identity and remain insertion targets. Generated/native instructions remain a separate, read-only inspection. Unsupported control flow remains explicit, with localized diagnostic explanations rather than a pretend group.

Import also recognizes return guards: a contiguous true arm whose known local paths all return is an ordinary editable **If**, with the false continuation left after it. It does not need a shared continuation instruction or an Else containing the remaining section. Instructions before the check stay unconditional, and existing fallthrough into the next section is retained. Export does not append an unreachable jump after an immediately returning body. Scheduled exits, cyclic or unresolved paths, and external entry into the proposed body remain explicit. This uses the same conditional identities, editing and history; it introduces no separate guard model. Import corrections require reimporting source scripts to reorganize previously saved explicit instructions.

The Instruction inspector exposes named fixed/repeated parameters, scalar words and word lists, references and detached SCPT expressions. **Edit parameter** opens the existing SCPT expression control or a paged target selector when appropriate. **Follow reference** navigates to the authored target. **Instruction timing** edits refresh and schedule expressions. **Insert instruction** uses the complete SPICE instruction catalog, including 265, without imposing platform-target availability rules.

**Insert If / loop / Switch** also offers Do While, For, Break and Continue. In Semantic mode, conditions appear on the If, Else If, While, Do While, For and Switch headers. Select a header and use **Edit condition** for the full expression. Long expressions are shortened only in the outline; the inspector and expression editor retain the full value. If/Else If/Else appear as sibling headers without an extra chain wrapper. The first If header still identifies the complete chain for copy, move and delete; use **Edit branches / cases** to add, remove or reorder individual branches, or edit Switch labels/default/fallthrough. Retained arms keep their IDs.

Supporting instructions live in the **Instruction inspector**, rather than adding Before check, Initialize, Update or Body wrapper rows to the Semantic tree. Loop and branch bodies appear directly under their headers. Headers summarize populated supporting sequences (for example, `2 instructions before check`). Select a construct to open its **Supporting instructions** section, choose a phase, and inspect its instructions using the same paged outline and editing actions. **Insert at phase start** works even when the phase is empty; **Select phase** selects that sequence as the target for inserting a nested construct. Selecting an instruction allows parameter editing, insertion after it, deletion and drag-and-drop reordering. Nested control flow remains browsable and editable within the phase. Following a reference or search result to a supporting instruction selects its containing construct in the Semantic tree and reveals the exact instruction and phase in the inspector. **Return to construct** returns selection to that header.

Use **Add preparation instruction** on a condition-bearing header to append instructions immediately before its check. If/Else If preparation runs only when that branch is reached. While preparation runs before the first check and every later check, including the final false check. Do While preparation runs after its body, before each check. For retains separate Initialize (once), Before check, Body and Update sequences internally; the inspector exposes its supporting phases. Continue follows the loop's normal check/update path, so preparation is not skipped. Body and Update are not preparation. Selecting a branch or loop header and inserting an instruction targets its body; selecting a body instruction inserts after it. Break/Continue requires a valid enclosing loop/switch target, checked by the engine. Each accepted operation is one journal command. These are views of existing owned sequences with stable identities, not a second editing representation. Instruction mode retains the explicit structural tree.

The **Text editor and preview** dock follows a selected string or an instruction's first text reference. It reuses the formatted/plain-text controls with detached values, rather than fake document locations. Typing stays in a local draft; **Apply** creates one history item and **Discard** reloads the committed text. An unapplied draft remains pinned while navigating. Conflicting changes retain the draft and prevent a stale Apply. Leaving the project requires handling that draft. The preview shows supported text/header/color/scale content; it is not a game renderer. **New string** creates indexed dialogue or indexed plain text. Footer-backed strings are created and edited directly on their instruction parameters; no separate text item or reference binding is needed. Deleting a referenced string fails with a diagnostic rather than leaving a dangling use.

Open **Navigator** from the View dock menu to browse opcodes, variables, incoming references, strings, incomplete instruction bindings or actions. Results are paged and queried explicitly; activation navigates to the selected item. Incoming action references and variable uses reuse resident indexes. Text-use and opcode scans run only on request and build labels for the returned page. Changed content invalidates displayed query results rather than automatically repeating a project query. **Back/Forward** uses shared session navigation history.

`TextEditorComponent`, `EditorQueryWidget`/`NavigatorComponent`, `ScriptEditingActions`, `InstructionInspector` and `ScriptOutlineComponent` use the Qt-free Editor contracts. ProgramBackend translates their drafts and intents to the single ProgramService journal. Imported and manually created constructs use these same operations. Parameter edits refresh local rows; structural edits refresh affected fetched containers. Group browsing reads stored bodies, including empty ones, without reconstructing an SCT or running grouping analysis. A separate per-sequence cache supplies diagnostics for remaining explicit control flow; it owns no groups.

G2 restores R01–R06 and R12 within these stated recognition/preview limits. It does not port the remaining productivity, module, language, story, resource or workspace tools. Those remain G3–G6. Existing full-value/advanced coordinator dialogs are retained until their component replacements are ready.

## Shared concurrency and fused dataset import

**Settings → Performance → Background concurrency** controls SALSA's shared background-worker budget. Automatic uses half the available logical CPU cores, rounded down, with a minimum of one. An explicit setting is saved for subsequent sessions. Dataset hashing and native import acquire permits from the same Qt-free budget, which future parallel export can also use. Export itself has not been parallelized by this change. Working-memory reservations can reduce concurrency below the selected count.

A fresh import reads each SCT once from its source. Its immutable capture binds those bytes to the computed digest, so SALSA baseline storage and normalization do not hash the same input again. SPICE retains responsibility for its own parser and provenance work. There is no size-limited source cache and no separate scan-then-reread import pass. Discovery reads file metadata, not SCT payloads; the scan reserves working memory before reading payloads, including a size check before allocation if a source changes. Normalized IR accumulates as the project's resident state, not as retained source or parser snapshots. The working-byte budget is a scheduling estimate, not a hard process-memory cap.

Only filenames, sizes, digests, text evidence needed for dataset convention selection, and normalized script results survive each worker. Results assemble in manifest order, preserving authored identity allocation regardless of completion order. Per-script baselines carry a pending dataset fingerprint only inside detached preparation; finalization assigns the completed scan fingerprint before anything becomes live or saveable.

Baseline bytes are written into a uniquely owned staging directory beside the destination workspace. Workers retaining identical revisions coordinate that one write and reuse the completed file; different revisions retain concurrently. After the full identity is accepted, the files move into the workspace baseline store (with a copy fallback for a custom component on a different volume). Cancellation or preparation failure removes the owned stage. Existing retained baselines are still checked when encountered. Saved checkpoints open without parsing SCTs; current-layout inspection and transaction recovery determine that path before the dataset scan. Unsupported development layouts fail visibly rather than activating a compatibility path.

Validation uses focused synthetic console checks for replenishment, shared admission/cancellation, source capture reuse, deterministic identity, checkpoint reopen, and abandoned-import cleanup. No GUI, corpus expansion, or phase-timing infrastructure is part of this change.


## One authoritative group model

SPICE structured-control-flow analysis is an import input, not a second editor model. Supported regions become the existing Conditional, Loop and Switch actions, Arm records, ConditionRegion records and owned Sequences. Nested groups normalize from children to parents. Their IDs, body ownership and conditions persist in the binary project and are shared by both editor views. New references do not automatically dissolve a group or replace its identity. User changes use ordinary history commands.

Empty sequences are valid bodies and remain editable even when no instruction occupies them. Deleting the last body item does not delete the group, its arm or its condition. Import retains controller and leaf action identities. Ordinary branch-exit/back-edge instructions can become scoped Break/Continue actions with their original identities and refresh behavior; these target the owning construct instead of a former physical continuation. Break can target an enclosing conditional as well as a loop or switch. Lowering derives the output instructions from this single authority.

Import currently normalizes contiguous conditional, While and explicit-default Switch regions whose continuation and body boundaries are known. Scheduled controllers, unsupported natural loops, ambiguous boundaries and unknown switch defaults remain explicit with explanations. Scheduled body instructions stay intact. This is a bounded normalization pass, not a claim that every native graph can be structured. Source SPICE graphs are discarded. Only diagnostics may be cached; neither opening a tree nor loading a checkpoint re-infers its stored group structure.

The private program binary schema is 5, preserving controller/transfer refresh behavior and editable productivity metadata. Container version and zstd encoding are unchanged. Previous development schemas are rejected rather than migrated; legacy Python SALSA v7 import remains supported. No submodule changes are required.

## G5 story, interaction and route tools

The Authoring menu provides Story workspace, Variable meanings, Script interactions, Route endpoints and Coordinated output as separate components over the same backend and history. New projects start in script-editing mode: instruction and semantic outlines, structured control flow, strings and ordinary editing remain available without story analysis. Opening a normal script tab or the disabled Story workspace does not start that analysis. Choose **Analyze and organize whole project** in the Story workspace to run the explicit, cancellable operation and review proposed module definitions. Analysis always covers every script in the project; there is no script-subset analysis scope. The script picker is a display filter only.

The review retains existing modules and offers unorganized code sections as starting boundaries, excluding init and loop. These are section suggestions, not inferred cutscene meanings. Select the definitions to add, then choose **Enable story authoring**; accepting is one undoable project change. Cancelling leaves authored state untouched. Unselected code stays editable; readers outside organized modules remain navigable relationship endpoints. The unorganized-section count makes remaining coverage visible.
